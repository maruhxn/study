프로듀서는 ==**레코드를 Kafka 토픽의 한 파티션에 발행하는 클라이언트**==다. 백엔드 개발자는 **어느 파티션에 보낼지, 언제 전송 성공으로 볼지, 실패를 어떻게 다룰지** 알아야 한다.

## 1. 레코드 전송 흐름

`레코드 생성 → 직렬화·파티션 선택 → 버퍼에 배치 → 전송 스레드가 리더 브로커로 전송 → 확인 응답`

![레코드 여러 개를 하나의 배치로 묶는 모습](https://images.ctfassets.net/gt6dp23g0g38/4QinkT7rPaVuBNxl7hDjgq/2a3f4a75025fcec086baef7a2d51e463/Kafka_Internals_018.png)

이미지 출처: [Confluent — Kafka 브로커 동작](https://developer.confluent.io/courses/architecture/broker/)

- **토픽·키·값**을 지정해 보낸다. 헤더·타임스탬프도 넣을 수 있다. **파티션**은 직접 지정한 번호나 프로듀서의 파티션 선택 로직으로 전송 전에 정해지고, **오프셋**은 브로커에 기록될 때 부여된다.
- **직렬화**: 키와 값을 전송 가능한 바이트로 바꾸는 과정. 소비자가 같은 형식을 해석하도록 JSON·Avro 등의 형식과 변경 규칙을 정한다.
- `bootstrap.servers`: 클러스터에 처음 접속할 주소. **브로커 주소를 여러 개** 적어 접속 지점 하나의 장애에 대비한다. 프로듀서는 여기서 토픽·파티션·리더 정보를 얻어 알맞은 브로커로 보낸다.

## 2. 키 선택

- ==**같은 키는 보통 같은 파티션**==으로 간다. 주문별 순서가 중요하면 `orderId`를 키로 쓴다. ex) 주문 `123`의 생성·결제 이벤트.
- **키가 없으면** 기본 파티셔너가 파티션을 선택한다. 관련 이벤트를 같은 파티션에 묶어야 한다면 키를 생략하지 않는다.
- 키가 있어도 **파티션 수나 파티셔너가 바뀌면 배정이 달라질 수 있다**. [[03 토픽·파티션 상세 개념]]의 증설 절차를 따른다.
- 이벤트가 한 키에 몰리면 ==**핫 파티션**==이 된다. 키는 순서가 필요한 업무 단위와 트래픽 분포를 함께 보고 고른다.

## 3. `send()` 반환은 저장 성공이 아니다

Java `KafkaProducer.send()`는 ==**비동기**==다. 대개 레코드를 프로듀서 메모리 버퍼에 넣고 곧바로 반환하므로, **콜백의 예외나 `Future.get()` 결과**로 전송 결과를 확인해야 한다. 성공의 의미는 `acks` 설정에 따르며, `acks=0`이면 성공으로 끝나도 브로커 저장 여부는 알 수 없다. 메타데이터 조회나 버퍼 부족 시에는 `send()` 자체가 잠시 막히거나 예외를 던질 수도 있다.

- **비동기 전송**: 완료 콜백에서 실패를 기록하고 대응한다. 호출 직후 “발행 성공”으로 처리하지 않는다.
- **동기 전송**: `send(...).get()`으로 결과를 기다린다. 흐름은 단순하지만 요청마다 기다리면 처리량이 낮아질 수 있다.
- 앱 종료 시 **`close()`**로 남은 전송을 완료한다. 현재 버퍼의 전송 완료만 기다려야 할 때는 `flush()`를 쓴다.

## 4. 저장 신뢰성: `acks`·복제·재시도

| 설정 | 성공으로 보는 시점 | 주의점 |
|---|---|---|
| `acks=0` | 브로커 응답을 기다리지 않음 | 저장 여부를 확인할 수 없음 |
| `acks=1` | 리더가 기록한 뒤 응답 | 팔로워에 복제되기 전에 리더 브로커에 장애가 나면 유실 가능 |
| `acks=all` | 현재 동기화된 복제본(ISR)이 기록한 뒤 응답 | 복제본 응답을 기다림; 내구성에 가장 유리 |

**ISR**은 리더를 따라잡고 있는 복제본 집합이다. `min.insync.replicas`는 `acks=all` 쓰기가 성공하려면 **ISR에 최소 몇 개의 복제본이 있어야 하는지** 정한다. ex) 복제 계수 `3`, `min.insync.replicas=2`, `acks=all`: ISR이 1개뿐이면 쓰기가 실패하고, ISR이 3개라면 3개 모두의 확인을 기다린다.

![ISR이 최소 개수보다 적어 전송에 실패하는 모습](https://images.ctfassets.net/gt6dp23g0g38/1w80a15fjW6XiLuZvZORxn/c15547a6e61ad1e2768f07eb157cdf58/Kafka_Internals_091.png)

이미지 출처: [Confluent — 내구성과 순서 보장](https://developer.confluent.io/courses/architecture/guarantees/)

실무에서 자주 쓰는 내구성 구성은 ==**복제 계수 `3` + `min.insync.replicas=2` + `acks=all`**==이다. 브로커 하나가 멈춰도 쓰기를 이어갈 수 있고, ISR이 2개 미만이면 성공 응답을 주지 않는다.

- **재시도**: 일시적 전송 실패는 프로듀서가 재시도할 수 있다. 최종 실패는 `delivery.timeout.ms` 등을 거쳐 애플리케이션에 전달되므로 **콜백·예외를 처리**해야 한다.

### 멱등 프로듀서

`enable.idempotence=true`이면 프로듀서가 **프로듀서 ID(PID)**와 **파티션별 시퀀스 번호**를 레코드 배치에 붙이고, 브로커는 이를 보고 ==**같은 배치를 다시 받으면 중복 기록을 막는다**==.

ex) 브로커가 이벤트를 저장했는데 성공 응답이 유실된 경우, 프로듀서가 같은 배치를 재시도해도 브로커는 PID·시퀀스 번호로 중복임을 알 수 있다.

![응답 유실 후 재시도할 때 PID와 시퀀스 번호로 중복을 막는 모습](https://images.ctfassets.net/gt6dp23g0g38/5NH8JBhOQWlZNiki8Ff5iE/b50426ae88cc1bdcfe12f1e9e5878c19/Kafka_Internals_092.png)

이미지 출처: [Confluent — 내구성과 순서 보장](https://developer.confluent.io/courses/architecture/guarantees/)

- **설정**: 최근 Kafka 클라이언트는 충돌하는 설정이 없으면 멱등성이 기본 활성화된다. `acks=all`, 재시도 허용, `max.in.flight.requests.per.connection ≤ 5`가 필요하다. 이 조건에서는 재시도 중에도 **한 파티션 안의 전송 순서**가 유지된다.
- **보장 범위**: 동일 프로듀서의 내부 재시도에 적용된다. 앱이 `send()`를 새로 호출해 같은 업무 이벤트를 발행하거나, 프로듀서 재시작 후 다시 발행하면 중복될 수 있다. 컨슈머 재처리와 외부 DB의 중복 반영도 별개다. 필요한 경우 **업무 이벤트 ID와 소비 측 멱등 처리**를 둔다.
- **장애 대응**: 멱등성을 켜도 최종 전송 실패는 날 수 있다. 실패를 무시하거나 무조건 새 `send()`로 재발행하지 말고, 업무상 재발행 기준을 정한다.

## 5. 처리량과 지연

- 프로듀서는 **파티션별로 레코드를 묶어 전송**한다. `batch.size`는 배치 크기, `linger.ms`는 추가 레코드를 기다릴 수 있는 최대 시간이다. 크게 조정하면 전송 효율이 좋아질 수 있지만 대기 시간도 늘 수 있다.
- `compression.type`으로 배치를 압축하면 네트워크·저장 공간을 줄일 수 있지만 CPU를 더 쓴다.

**처음에는 기본값으로 시작해** 발행 실패·전송 지연·처리량을 측정한 뒤 조정한다. 설정 기본값은 클라이언트 버전에 따라 달라질 수 있다.

### 버퍼

- **구조**: `send()`로 넘긴 레코드는 프로듀서 메모리의 버퍼에 ==**파티션별 배치**==로 쌓인다. 별도 전송 스레드가 보낼 수 있는 배치를 꺼내 브로커별 요청으로 묶어 보낸다. 내부 구현 이름은 `RecordAccumulator`다.
- **전송 시점**: 배치가 `batch.size`(기본 16KB)만큼 차거나 `linger.ms`(Kafka 4.0부터 기본 5ms)가 지나면 보낼 수 있는 상태가 된다. 배치가 다 찰 때까지 무조건 기다리지는 않는다.
- **`buffer.memory`**(기본 32MB): 전송을 기다리는 레코드가 쓸 수 있는 전체 메모리. 파티션별 배치가 모두 이 공간을 나눠 쓴다.
- **버퍼가 가득 차면**: 레코드가 브로커로 나가는 속도보다 빨리 쌓이면 ==**`send()`가 최대 `max.block.ms`(기본 60초)까지 막힌다**==. 이 시간은 메타데이터 조회 대기와 합산되고, 넘기면 `BufferExhaustedException`으로 실패한다. 웹 요청 스레드에서 `send()`를 호출하면 요청 처리도 함께 멈출 수 있다.
- 버퍼 부족은 **브로커 전송이 밀린다는 신호**로, 컨슈머 처리량에 맞춘 자동 유량 제어와는 다르다.
- **두 가지 대기 시간**: `send()` 안에서 메타데이터 조회·버퍼 공간 확보를 기다리는 시간은 `max.block.ms`가 제한한다. 버퍼에 들어간 뒤의 시간은 `delivery.timeout.ms`(기본 2분)가 제한한다. 이는 `send()` 반환 뒤 성공·실패를 알리기까지의 상한으로, 버퍼에서 전송을 기다린 시간·응답 대기·재시도 시간을 모두 포함한다. 넘기면 콜백으로 실패가 전달된다.
- **버퍼는 메모리다**: 프로세스가 강제 종료되면 ==**아직 전송되지 않은 레코드는 사라진다**==. `acks=all`도 브로커에 도착한 뒤의 보장이다. 정상 종료 시 `close()`로 남은 레코드를 보내고, `close(Duration)`의 시간이 지나면 남은 레코드는 실패 처리된다.

## DB 저장과 발행

주문 서비스가 DB에 주문을 저장하고 `orders.events`에 이벤트를 발행할 때, ==**DB 저장 성공과 Kafka 발행 성공은 별개**==다. 둘을 함께 보장하는 설계는 **Transactional Outbox**에서 따로 다룬다. Kafka 트랜잭션만으로는 일반 DB 쓰기까지 원자적으로 묶이지 않는다.

## 참고

- **`max.in.flight.requests.per.connection`과 재시도 중 순서**: 멱등성이 꺼진 상태에서 여러 요청을 동시에 보내면 재시도로 순서가 바뀔 수 있다.
- **Kafka 트랜잭션**: 여러 파티션에 원자적으로 발행하거나, Kafka 안의 소비·생산 파이프라인에서 오프셋과 출력을 원자적으로 처리할 때 쓴다.
- **버전 차이**: 참고 글의 일부 설정값은 작성 당시 클라이언트 기준이다. 최근 버전에서는 멱등성이 기본 활성화되고 `linger.ms` 기본값도 달라졌다. **운영 중인 클라이언트 버전의 설정 문서**를 확인한다. `min.insync.replicas`는 *확인이 필요한 ISR의 최소 크기*로, `acks=all`이 그 수만큼만 응답을 기다린다는 뜻은 아니다.
