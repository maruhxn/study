컨슈머는 **토픽의 파티션에서 레코드를 가져와 처리하는 클라이언트**다. 백엔드 개발자는 **누가 어느 파티션을 읽는지, 처리 완료를 어디에 기록하는지, 장애 뒤 무엇을 다시 처리하는지** 알아야 한다.

## 1. 읽기 흐름

`토픽 구독 → 파티션 할당 → poll()로 레코드 가져오기 → 업무 처리 → 오프셋 커밋`

- `group.id`가 같은 컨슈머는 **한 그룹**으로 일을 나눈다. 다른 그룹은 같은 토픽을 따로 읽는다. ex) 결제 그룹과 알림 그룹이 `orders.events`를 각각 소비한다.
- 컨슈머는 `poll()`로 브로커에서 레코드를 **가져온다**. `key.deserializer`·`value.deserializer`로 바이트를 해석한 뒤 업무 로직을 실행한다. 형식은 프로듀서의 직렬화 형식과 맞아야 한다.
- 한 그룹에서 ==**파티션 하나는 한 시점에 한 컨슈머에 할당**==된다. 한 컨슈머는 여러 파티션을 맡기도 한다. 단일 토픽에서 컨슈머가 파티션보다 많으면 남는 컨슈머는 유휴 상태다.

## 2. 읽은 위치와 처리 완료 위치는 다르다

- **현재 위치(position)**: 다음 `poll()`이 돌려줄 레코드의 오프셋. 가져온 레코드만큼 앞으로 간다. **업무 처리 완료를 뜻하지 않는다.**
- **커밋 오프셋**: 장애·재시작·리밸런싱 뒤 **다음에 읽을 위치**. 그룹·토픽·파티션별로 Kafka의 `__consumer_offsets`에 저장된다.
- ex) 오프셋 `42`까지 처리했다면 **`43`을 커밋**한다. `42`는 다시 읽지 않겠다는 뜻이다.

![컨슈머 그룹이 처리 위치를 코디네이터에 커밋하는 모습](https://images.ctfassets.net/gt6dp23g0g38/F1Nqrh5ElviKJKLuzO6gn/73a3f20420af1749bc74d2d7528cbf45/Kafka_Internals_071.png)

이미지 출처: [Confluent — Consumer Group Protocol](https://developer.confluent.io/courses/architecture/consumer-group-protocol/)

### 커밋 방식

| 방식 | 동작 | 실무에서 주의할 점 |
|---|---|---|
| 자동 커밋 (`enable.auto.commit=true`) | 읽은 위치를 주기적으로 커밋 | 처리 완료 시점과 커밋 시점이 어긋날 수 있음. 워커 스레드에 작업만 넘기고 다음 `poll()`을 하면 미완료 작업까지 커밋될 수 있음 |
| 명시적 커밋 (`enable.auto.commit=false`) | 업무 처리 **완료 후** 직접 커밋 | 처리 완료 후 커밋 전에 장애가 나면 다시 처리될 수 있음. 비동기 커밋은 실패 콜백도 확인 |

- **인자 없는 `commitSync()`·`commitAsync()`**: 마지막 `poll()` 위치를 커밋한다. 받은 레코드를 모두 처리했을 때 쓴다.
- **일부만 처리했을 때**: 파티션별로 **처리 완료 위치의 다음 오프셋**을 명시해 커밋한다.
- ==**성공적으로 처리한 레코드까지만 커밋**==한다. 한 파티션에서 앞 레코드가 실패했는데 뒤 오프셋을 커밋하면 재시작 후 실패한 레코드를 건너뛸 수 있다.
- 외부 DB 저장과 Kafka 오프셋 커밋은 별개 작업이다. **중복 처리에 안전한 업무 로직**이 필요하다.

### `auto.offset.reset`

- 커밋 오프셋이 없을 때, 또는 로그 보존 정책 등으로 커밋 오프셋이 유효 범위를 벗어났을 때 적용된다.
- `earliest`는 남은 레코드의 처음부터, `latest`는 현재 끝부터 읽는다.
- **유효한 커밋이 있으면 `earliest`여도 처음부터 다시 읽지 않는다.** 재처리는 오프셋을 명시적으로 재설정하거나 `seek()` 등을 쓴다.

## 3. 리밸런싱: 담당 파티션 변경

컨슈머 추가·종료·장애, 토픽 파티션 증가 등이 생기면 **그룹의 파티션 담당자를 다시 정한다**. 이 과정이 리밸런싱이다. 이전 컨슈머의 **미완료 작업과 커밋 위치**도 함께 봐야 한다.

![컨슈머가 추가될 때 기존 담당 파티션을 반납하고 재할당하는 전통적 리밸런싱](https://images.ctfassets.net/gt6dp23g0g38/3AvvIpWKyXtRxH8g8Oev5j/d8255b0fa80975f2b0b0febe772c52f9/Kafka_Internals_076.png)

이미지 출처: [Confluent — Consumer Group Protocol](https://developer.confluent.io/courses/architecture/consumer-group-protocol/) · **그림은 전통적 전체 중단 방식**. 협력적·새 그룹 프로토콜은 영향을 받는 파티션만 단계적으로 옮길 수 있다.

- `poll()` 호출 간격이 `max.poll.interval.ms`를 넘으면 그룹은 컨슈머가 처리를 이어가지 못한다고 보고 파티션을 재할당할 수 있다. 처리가 오래 걸리면 `max.poll.records`(한 번에 받는 레코드 수)와 처리 시간부터 맞춘다.
- 리밸런싱 중 담당 파티션을 잃으면 커밋이 실패하거나, 다른 컨슈머가 마지막 커밋 위치부터 다시 읽을 수 있다. **처리 완료 → 커밋** 순서를 지킨다. 필요하면 `ConsumerRebalanceListener`에서 파티션 반납 전에 완료된 작업을 정리한다.
- **영향 범위는 리밸런싱 방식과 프로토콜에 따라 다르다.** 그룹 전체가 매번 멈추지는 않는다. 배포 때는 중복 처리와 일시적 지연을 예상하고 랙을 확인한다.
- Kafka 4.x의 새 `group.protocol=consumer`는 **기본값이 아니다**. 기존 `classic`과 리밸런싱 동작이 다르니 운영 버전·설정을 확인한다.

## 4. 병렬 처리와 순서

- **컨슈머 인스턴스 추가**: 가장 단순한 확장 방식. 파티션을 나눠 맡긴다.
- Java `KafkaConsumer` **인스턴스 하나를 여러 스레드에서 동시에 호출하면 안 된다**. 스레드를 늘리면 스레드마다 컨슈머를 따로 둔다.
- **워커에 넘기기**: 한 컨슈머가 `poll()`한 레코드를 여러 워커에 나눠 주는 방식. **워커 완료 순서가 뒤바뀔 수 있고**, 완료 전에 오프셋을 커밋하면 유실될 수 있다.
- 주문별 순서가 중요하면 같은 파티션의 작업은 순서대로 완료시킨다. 커밋은 파티션별로 **앞선 레코드가 모두 처리된 지점을 확인하고 그다음 오프셋**으로 한다.
- 처음에는 파티션별 순차 처리로 시작한다.

## 5. 운영: 컨슈머 랙

**랙(lag) = 파티션 로그 끝 오프셋 − 그룹의 커밋 오프셋.** 그룹·파티션별로 본다. 현재 값은 `kafka-consumer-groups.sh --bootstrap-server <broker> --describe --group <group>`으로 확인한다.

- 랙이 **계속 늘면** 유입량이 처리량보다 큰지, 소비가 멈췄는지 본다. 특정 파티션만 크면 핫 파티션이나 해당 컨슈머 장애도 살핀다.
- 랙이 **줄면** 밀린 데이터를 따라잡는 중이다. 처리 전에 오프셋을 커밋했다면 랙이 낮아도 실제 업무 처리는 끝나지 않았을 수 있다.
- `pause()`/`resume()`으로 특정 파티션의 읽기를 잠시 멈췄다 다시 연다. **생산 속도는 줄지 않는다.** 과부하가 계속되면 처리량·생산량·보관 기간을 함께 조정한다.

## 실무 판단 예시

- 결제 컨슈머가 DB에 결제 결과를 저장한다면 ==**DB 처리 성공 후 오프셋을 커밋**==한다.
- 저장은 성공했는데 커밋 전에 장애가 나면 같은 이벤트가 다시 온다. **이벤트 ID나 업무 키로 중복 반영을 막는다.**
- 실패 레코드를 무조건 건너뛰거나 뒤 오프셋을 먼저 커밋하지 않는다.
